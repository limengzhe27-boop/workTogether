# WorkTogether contract v1

Status: ready for independent acceptance tests. Python 3.9+, standard library only.
Production modules: `worktogether/`. Antigravity owns `qa/antigravity/` and
`tests/acceptance/antigravity/`; do not modify production modules to pass tests.

## Public CLI

All commands: `python3 -m worktogether --db PATH COMMAND ...`.
Output: one JSON object to stdout. Success exit 0; domain/input error exit 2 with
`{"error":{"code":"...","message":"..."}}`. No model is called implicitly.

- `project-add --name NAME --path EXISTING_DIRECTORY`
- `task-add --project PROJECT_ID --title TITLE --requirement TEXT`
- `show --task TASK_ID`: task, steps, dispatches, events (chronological).
- `dispatch --task TASK_ID`: issue at most one eligible work item. Returns
  `{"dispatch": object|null}`. Repeated calls never reissue active work.
- `submit --task TASK_ID --file REPORT_JSON`: atomically validate and ingest.
- `pause --task TASK_ID`; `resume --task TASK_ID` (only PAUSED).
- `retry --task TASK_ID --dispatch DISPATCH_ID`: explicitly retry BLOCKED dispatch;
  increments attempt, invalidates old dispatch. Not allowed at repair limit.
- `expire --task TASK_ID`: block expired ACTIVE dispatches; never auto-relaunch.
- `template --task TASK_ID --dispatch DISPATCH_ID`: output editable result JSON.
- `handoff --task TASK_ID --dispatch DISPATCH_ID`: task-scoped manual package,
  containing dispatch payload, report template and instructions.
- `doctor --project PROJECT_ID`: Git status, executable availability; no mutation.
- `demo`: isolated mock full cycle in this database; explicitly marked simulated.

Python public API: `from worktogether.core import Engine, CollabError`.
`Engine(db_path)`; methods `project_add(name,path)`, `task_add(project,title,requirement)`,
`show(task)`, `dispatch(task)`, `submit(task,report)`, `pause(task)`, `resume(task)`,
`retry(task,dispatch_id)`, `expire(task)`, `template(task,dispatch_id)`, `doctor(project)`.
IDs are opaque strings. API domain errors expose `.code`. Engine opens a transaction
per operation and supports independent instances against the same database.

## State and dispatch

Task status: ACTIVE, PAUSED, BLOCKED, COMPLETED. Task phase: PLANNING,
PLAN_REVIEW, PLAN_FINALIZE, EXECUTING, COMPLETED. One review round, then Codex
finalizes (cannot submit another review). Task requirements are immutable in v1.
Plan step: id, title, acceptance (nonempty string list), depends_on (step IDs).
The dependency graph must be acyclic. Finalization may edit the reviewed draft.

Step status: PENDING, CODING, VERIFYING, FIXING, COMPLETED, BLOCKED.
Independent steps may overlap one Codex dispatch and one Antigravity dispatch per
task. Dependencies require COMPLETED. Two active Codex jobs for the same project
are prohibited (shared checkout); verification must target immutable versions.
v1 does not create worktrees or test environments automatically.

Dispatch: id, task_id, step_id|null, role (codex|antigravity), kind
(PLAN|PLAN_REVIEW|PLAN_FINALIZE|CODE|VERIFY|FIX), attempt, version|null,
status (ACTIVE|DONE|BLOCKED|SUPERSEDED), created_at, deadline, payload.
Default timeout 1800 seconds; max repairs 2. A dispatch is durably recorded before
any external handoff. Restart preserves ACTIVE work without launching it again.
Exact-once external process execution is NOT claimed. Unknown/expired executions
block until explicit retry. Replaying a saved result is safe.

## Report envelope (all fields required, unknown fields rejected)

```json
{
  "schema_version": 1,
  "task_id": "TASK_ID",
  "dispatch_id": "DISPATCH_ID",
  "role": "codex",
  "attempt": 1,
  "status": "DONE",
  "summary": "Outcome",
  "basis": ["Concrete source or observation"],
  "suggestions": [],
  "next_action": "Requested next action; scheduler retains authority",
  "data": {}
}
```

Nonempty summary, basis (nonempty strings), next_action required. Suggestions is
a string list, max 3 for PLAN_REVIEW. Status by dispatch:

| kind | status | data |
|---|---|---|
| PLAN / PLAN_FINALIZE | DONE | `{"steps":[{"id":"s1","title":"...","acceptance":["..."],"depends_on":[]}]}` |
| PLAN_REVIEW | DONE | `{}` |
| CODE / FIX | DONE | `{"version":"immutable commit or snapshot identifier","changes":["..."],"known_limits":[]}` |
| VERIFY | PASS / FAIL | `{"version":"exact dispatch version","checks":[{"criterion":"exact acceptance string","status":"PASS or FAIL","evidence":["artifact reference or concrete command/result"]}],"findings":[]}` |
| any | BLOCKED | `{"reason":"..."}` |

Every acceptance criterion must occur exactly once in verification checks. PASS
requires every check PASS and no findings. FAIL requires at least one FAIL and at
least one finding `{ "problem":"...", "reproduction":["..."], "expected":"...",
"actual":"...", "evidence":["..."] }`. Evidence references are recorded, not
independently authenticated by the scheduler; PASS is a reported verdict.
Known limits cannot alter acceptance. FIX must submit a different version.

Duplicate identical report for an already accepted dispatch returns
`{"accepted":true,"duplicate":true}` without new events. Different result for
that dispatch: CONFLICT. Wrong task/role/attempt/version: reject, no state change.
Malformed report: INVALID_REPORT. Stale dispatch: STALE_REPORT. Unknown IDs:
NOT_FOUND. Invalid transition: INVALID_STATE. Invalid plan: INVALID_PLAN.

Paused tasks accept already-issued results but remain PAUSED; no new work until
resume. BLOCKED results and timeouts block task and dispatch without counting a
code repair. Explicit retry restores original step activity, gets a new dispatch
ID and attempt. First and second failed verifications schedule FIX 1 and FIX 2;
failure after FIX 2 blocks with REPAIR_LIMIT and cannot be retried via CLI.

## Artifacts and boundaries

SQLite is authoritative. JSON/Markdown files are handoff artifacts, never trusted
as commands. No shell evaluation of model output. `template` emits JSON to stdout;
caller may save it to a file. Evidence and Markdown can live beneath a task-specific
artifact directory. Git dirty status is diagnostic, not an automatic reset/cleanup.
Manual mode is implemented first. Simulated mode validates orchestration only.
Real provider session persistence, worktree provisioning, automatic launching,
metrics and browser UI are subsequent milestones, not implied by v1 core tests.
