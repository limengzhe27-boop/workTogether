# WorkTogether 现状与下一步（2026-10-11 修订）

## 目标与已实现的可用范围

目标是让一个项目中的多个 Agent 围绕同一任务讨论、分工、交付和验收，同时不干扰其他项目会话。岗位不再按品牌固定：任务团队可选择协调者，成员按实际适配器能力认领，平台校验唯一执行者与不同的验收者。

当前已实现任务团队、两轮并行意见/认领、三次集中规划、能力分工、独立验收、用户一次明确授权后的有界执行，以及原有的持久化、依赖、两次修复上限、暂停/重试与手动交接。新建任务页可一次提交启动团队；群聊现为有界并行广播并支持 Agent 互发消息，写入按项目串行。Harness 后台适配器默认关闭，启用后可认领编码；API Agent 仅能规划、复核与分析传入材料，不能直接读仓库或运行测试。

本轮新增流程经模拟 CLI、假 HTTP 服务、真实浏览器操作验证；Harness CLI 帮助与权限配置合成经本机无模型探测。未进行本轮三种真实模型的完整交叉开发验收。详见 `team-workflow.md`、`harness-adapter.md` 和 `team-development-plan.md`。

- 自动 CODE/FIX → VERIFY 现对 Git 可见文件做交付与验收前后漂移检查；模拟测试覆盖修改后阻断和无变化通过。尚未用真实 Agent 验证这一保护，也未生成固定快照。手动交接、非 Git 目录、Git 忽略文件和并发竞态仍需单独解决。
- 自定义 OpenAI 兼容 Agent 可由用户主动发送一次不含任务内容的短请求来测试接口响应；注册和打开页面不会自动调用。该检查可能产生少量模型用量，只证明基本连接与聊天返回形状，尚未证明真实任务分工可用。
- 运行详情可按需查看五种受限产物（指令、结果、事件、错误和启动参数），大文件最多预览 512 KB；没有自动拉取完整日志或扩大文件读取范围。
- 本机回环假服务已完成真实 HTTP 闭环：连接检查、三 Agent 顺序讨论、API Agent 接收前两位回复、计划批准后的分析交付、Antigravity 验收和依赖 Codex 步骤。未访问外网或付费模型；这不是 DeepSeek/Ollama 实际可用性的证明。受限沙箱无法绑定回环端口时，该集成测试会明确跳过。

## 2026-10-11 补记二：项目群聊（真并行 + 互相派活 + 默认可写）

用户明确期望：几个客户端 Agent 同时在一个项目里与其对话，互相讨论、提问、派活、领活，并且能在项目里干活。原先实现是"一次只叫一个 Agent 的排队对话"，`proposals` 只是给人看的建议，平台从不执行。本轮按用户选定的三项取舍重做对话层：

- **读/讨论全并行，写操作串行**（用户选择）。
- **选了项目就默认可写**（用户选择）：会话配置 `allow_write` 默认 `true`，可在输入框随时关闭。
- **默认最多 2 轮自动往返，可随时暂停**（用户选择）：`max_auto_rounds` 默认 2。

实现：

- 第 1 轮为真正的广播：一次事务内为每位成员签发 dispatch，各自独立会话进程并行执行，且**不注入同伴回复**；第 2 轮才交付上一轮全部发言。
- Agent 回复可携带 `data.messages:[{to,intent,content}]`（`ask`/`assign`/`claim`/`report`，每次最多 3 条）。平台校验目标是否在本房间、能力与预算后，写入一条真实的 Agent 发起群消息并触发下一轮；`claim`/`report` 为告知型，不消耗预算也不等待回复。
- 房间成员 = 任务团队（若有）∩ 已启用且就绪的 Agent；关闭或未配置的 Agent 不能被派活。
- 预算耗尽后的跨 Agent 消息进入 `HELD`，界面显示“让他们继续”，由用户显式释放并刷新预算。
- 写入串行：每轮最多一位成员持有写沙箱（优先具备编码能力者），并且**跨任务**检查同一项目是否已有 `CODE/FIX` 或持写 `CHAT` 在运行；其余成员并行只读，需要改动时用 `assign` 交接。
- 中断仍不自动重放：某位成员的进程失败时整轮标记 BLOCKED，其余成员的结果保留，可显式“重试/跳过”。

验证：`python3 -m unittest discover -s tests -q` 256 项通过（新增群聊、互发、预算、写入串行与归一化用例）；`cd web && npm test` 12 项通过；真实浏览器（1046×653）+ 本机桩 CLI 端到端跑通：一条广播 → 两位同时作答 → Codex 向 Antigravity 提问并收到回答 → 预算耗尽后消息进入“等待你确认”并可由“让他们继续”释放。全程未调用任何真实模型。

## 2026-10-11 补记三：接上真实模型，并修掉"派活拿不到写权限"

用户指出 Codex 随 ChatGPT 订阅提供。核实后确认：Codex CLI 0.162 就在 `/Applications/ChatGPT.app/Contents/Resources/codex-cli/`，且 `codex login status` 显示已用 ChatGPT 登录，只是不在 PATH 上（应用启动时创建 PATH 别名被系统拒绝）。已加入自动探测：PATH 优先，其次应用自带副本，显式路径始终优先。

随后用真实 Codex + 真实 Antigravity 跑通了完整闭环（细节见 [qa/group-room/acceptance.md](../qa/group-room/acceptance.md)）：项目上下文对真实模型生效；两位并行作答；第 2 轮 Antigravity 明确回应了 Codex 上一轮的发言；让只读的 Antigravity 派活给 Codex 后，Codex 真的改写了 `tests/test_app.py` 并跑通测试，事后在磁盘上独立复核。

真实运行也暴露了三个只有真模型才会碰到的问题，均已修复：

1. **`assign` 永远拿不到写权限**：Agent 发起的群消息没有继承会话写入授权，`_pick_writer` 直接放弃，于是两个真实 Agent 都回报"本轮只读，等拿到写权限再实施"。现改为继承会话授权。
2. **写入回合会被授予不能写的适配器**：Antigravity 适配器固定只读 plan 模式，却可能被选为唯一写者，得到一句做不到的授权。新增 `AgentConfig.writable`，`_pick_writer` 只考虑"有 code 能力且适配器可写"的成员；没有合适人选就不给写权限，而不是给一个假的。
3. **Antigravity 在对话里跑 `ls` 被拒，整轮作废**：33k token 白烧且回答被丢弃。现在 CHAT 提示明确要求用只读文件工具、命令被拒就用手上内容继续；并且命令被拒不再丢弃可用回答，改为在回答开头如实标注被拒命令，只有 VERIFY 仍严格失败。

- 界面新增**改动归因**：会改文件的回合在运行前后拍工作区快照，回复上标出「改了 N 个文件」并列出 M/A/D 路径；没有授权却改了文件也会被记录。快照是"大小+修改时间+开头 4 KB"，不是内容仓库，也不能证明改动完全由该 Agent 造成（同一时间窗内的人工编辑同样会被算进去）。

尚未验证：真实模型下的长会话、多任务并发与 Token 成本对照。

## P0-4：固定房间范围与可撤销写入授权（2026-10-11）

- 用户每条消息的所选成员构成固定范围；Agent 后续 ask/assign 只能点名范围内的成员，不能通过 all 广播派活或招入新启用的成员。输入框展示范围、发送明确 ID，并从服务端读取本任务可选成员。
- 新会话和缺少配置的旧会话默认只读，已有存储的开关值保留。单条只读限制沿委派链传递；可写请求中暂时只读的同伴仍可把工作交给范围内另一位成员，维持单写者协作。
- 关闭开关使旧授权代次失效，重新开启/重试/释放 HELD 不会恢复旧写授权；启动进程前在同一数据库锁内再核对成员和权限。已登记的旧写派发被拦截后留下 FAILED/BLOCKED 与显式恢复入口，不自动重放；已启动进程不会被强杀。
- 群聊写入与正式 CODE/FIX/VERIFY 共享项目占用边界，未解决的 BLOCKED 写者也不能被另一条通道绕过。无范围的历史自动消息要求跳过并重新选择成员发送，保留原始记录。
- 验证：新增 17 项后端与 2 项界面测试，完整后端 **319 项**、前端 **16 项**及生产构建通过，发布静态包同步更新。模拟 CLI + 内存 HTTP 跑通两轮广播、同伴提问及回复（5 次模拟运行），三种 CLI 均验证“登记后撤权，不启动进程”。未调用真实模型，未改真实状态库或密钥文件。
- 这不是 worktree/操作系统隔离，未验证 Antigravity 真实写入或真实模型的长会话成本；P0-1 仍待用户授权实测。

## P0-4 补记：API 请求准入也遵守房间边界（2026-10-11）

- 排查 P1-5 工具回路前发现：CLI 启动已复查成员，API 分支却只复查任务状态；请求构造之后发生的暂停也会漏检。先用模拟传输复现，再补齐 API 准入门禁。
- API 在请求准备完成后、登记 RUNNING 时复核原消息范围、当前团队/就绪状态、任务/派发状态和分析审批，明确拒绝写入派发。清除唯一密钥后，不再向已失去就绪资格的聊天成员发送带缓存密钥的请求。
- 未准入请求拒绝后保存 FAILED/BLOCKED 与可核查原因，不发 HTTP、不重试。已准入请求不能撤回，网络等待不占数据库锁；暂停仍可生效，返回结果允许保存但不启动后续调用。
- 新增 7 项回归（其中 6 项在修复前失败）；完整后端 **326 项**、前端 **16 项**及生产构建通过。已有本机回环 HTTP 测试也通过，无跳过；静态包重建无差异。只用临时数据库和模拟服务，无真实 Agent 调用，未修改真实数据或启动/停止服务。
- 本次没有增加文件/命令工具，API Agent 仍仅处理传入材料；未放宽成员、写入、预算、失败恢复或沙箱边界。P1-5 应先实现显式授权的只读工具回路，再验证隔离写入/命令执行器，不直接执行模型给出的 shell。

1. **真实项目的无人值守闭环**：隔离样例已通过，但 Antigravity 的工具权限拒绝仍可能让需要运行命令的验收停止。平台提供手动交接与报告提交，不绕过权限，也不把隔离样例当作真实项目验收。
2. **任意本地 Agent 接入**：Harness 0.2.0-rc.2 已有真实读取和创建文件样例；尚无任意工具权限或三种真实模型交叉开发的完整验收。Claude Code/ZCode 原生 CLI 适配器未实现；OpenAI 兼容接口接入不能代替原生编码工具能力。
3. **安全并行编码**：没有隔离 worktree、固定被测提交和合并审查，不能让多个编码 Agent 同时修改同一目录。现阶段同一项目的 CODE/FIX/VERIFY 派发互斥，自动 Git 交付另有有限的漂移检测；不同项目仍可独立推进。新增的“允许修改”只按消息授予写入沙箱，**不**构成版本隔离；逐文件还原也不会保留被覆盖的改动。这不能阻止平台外的手动编辑，也不能替代真正的版本隔离。
4. **效率结论**：没有真实的单 Agent 与多 Agent 同题对照数据，因此不能承诺节省 Token、成本或时间。
5. **界面深度**：页面可展示运行记录、报告、限定产物预览、项目 Doctor、项目记忆与文件清单、Git 变更与逐文件还原；任意文件内容浏览、内置 CLI 的认证检测和可靠的用量对比仍未接入页面。

## 下一轮优先级

1. 使用用户明确指定的真实小任务，在不扩大工具权限的前提下检验代码修改与需要运行测试命令的验收；记录权限结果、实际用量和失败原因。若仍受阻，保持手动验收为可用路径。
2. 定义版本隔离和只读测试环境，避免验收时 Codex 的后续改动污染被测版本；再考虑分析与测试准备的有限流水线重叠。
3. 先做用户允许的 Harness 短小真实连通测试，再用临时项目验证非 Codex 编码与另一 Agent 验收；失败保留证据，不扩权绕过。随后按实际需求选一个其他 CLI 扩展，不把任意命令字符串暴露给 Web 注册接口。
4. 真实对比 Codex 单独完成与协作模式：记录任务质量、Codex Token、总耗时、人工介入次数和误报。仅根据实测结果调整分工。

任何新能力都应先有端到端证据，再更新 README 和界面中的“可用”描述。
