# 有限讨论、能力分工与独立验收

## 接口与兼容性

在首次派发前，`POST /api/tasks/{task_id}/team`，请求示例：

```json
{"members":["codex","antigravity","local-model"],"coordinator":"local-model","reviewer":"codex"}
```

成员必须已经配置。协调者与方案复核者可省略，由已配置能力确定；必须不同。固定团队后，“全部”广播只发给本任务成员，不发到其他 Agent。进入派发后不能替换成员。没有配置团队的旧任务保持原有三次规划流程。

原有 `/discuss` 接口对团队任务执行以下有界流程：

1. `CONSULT`：所有成员各一次只读独立建议，并行上限 4。报告 `data={}`。
2. `PLAN`：协调者接收意见，输出含依赖和验收项的计划。
3. `CLAIM`：所有成员各一次申报，可读首轮意见和任务计划。报告 `data={"claims":[{"step_id":"s1","reason":"具体依据"}]}`，可空数组，不允许重复或越权认领。
4. `PLAN_REVIEW`：不同的方案复核者看计划及所有认领，最多三条实质建议。
5. `PLAN_FINALIZE`：协调者收敛；平台校验执行者与独立验收者，不符合能力或团队边界则拒绝。

总调用上限为成员数 × 2 + 3，2–12 名成员。报告身份、修订号、幂等、超时和失败恢复仍沿用现有契约。不自动重试不明状态。失败的单次派发需检查后显式重试，已完成轮次不会再次调用。模型讨论只决定候选方案，不自动扩大授权。

## 分工

步骤新增可选字段 `verifier` 和 `assignment_reason`。执行者按 `work_kind` 检查 `code` 或 `analysis` 能力。验收者需 `verify` 且不能为执行者自身。

最终方案显式提名优先；没有提名时优先考虑合法认领，再按本计划分工负载与稳定顺序择一。多个 Agent 认领同一项只能有一个负责人。认领理由作为上下文，不被视为已经证明的技术优势；当前没有基于历史质量自动评分。

普通 API 适配器支持 `plan/review/chat/analysis`，不支持 `code/verify`，且不会读取本地仓库。适配器能力不等于账户已登录、额度可用或权限充分。

## 当前范围

### 一次授权的自动流程

新团队任务可选择 `POST /api/tasks/{id}/delegate-team`，请求必须明确为 `{"authorize_execution":true}`。这表示授权团队围绕当前需求讨论并执行，不再等待定稿后逐步确认；普通 `/discuss` 仍只讨论、不执行。

自动作业持久化当前需求、修订号、团队与预算（成员数 × 2 + 15，即讨论加最多 12 次执行/验收调用）。定稿后只有授权范围未变、任务仍活跃、没有新消息待处理，才会记录委托批准并开始执行。暂停、失败、预算耗尽和未知运行均停止，不自动续费或重放。作业结束不一定表示任务完成。`GET /api/tasks/{id}/team-jobs` 可查看状态，恢复入口与其他作业相同。

任务批准不等于模型工具权限，也不是对需求外变更的授权。当前仍依赖模型遵循任务边界，不能自动证明方案没有语义上的范围扩大；对高风险任务应选先审方案模式。

新建页的“创建并授权团队执行”按创建、配置、启动顺序调用这些接口；若中途失败，保留并打开已创建任务，不会偷偷重新创建或重复执行。需求修订到新版本后允许重新选择团队；历史派发保留审计，但不锁住新版本的配置。旧待处理消息标记为需要重新审阅。
