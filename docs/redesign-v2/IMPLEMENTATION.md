# V2 开发边界与实施顺序

## 产品目标

一个项目入口管理需求、有限轮讨论、实施与验收。不同 Agent 通过平台传递任务产物，不是共享桌面聊天窗口。每个任务分别绑定 Codex 与 Antigravity 会话 ID，禁止使用“最近一次会话”恢复。项目间不能共享任务消息；账户额度、CPU 等资源仍可能相互竞争。

## 先打通，再美化

1. P0：真实 Codex 提案 → 指定 Gemini 3.8 Flash High 审查 → 原 Codex 会话定稿；最多三次调用，定稿后必须停止，不自动执行代码。
2. P1：按 DESIGN.md 重做界面，统一 React/Vite 构建来源。接通真实项目、任务、时间线；没有后端支持的能力明确禁用，不能模拟成功。
3. P2：增加需求修订与用户消息接口、显式批准开发、后台执行入口与配置。前端不能提交任意本机可执行路径。批准必须绑定任务需求与方案版本；修改需求使旧批准失效。
4. P3：隔离被测版本、有限返工与流水线。测试必须标明实际版本；依赖未完成的任务不可提前执行。未实现版本隔离前不开放同项目并发修改与验收。

## 必需的保护

- 不以文件更新或 UI 显示“完成”判定成功；以终止事件、会话身份、合法报告三者共同确认。
- 同一派发只能启动一次；未知进程不自动重跑。恢复前确认旧进程停止，再由用户明确重试。
- 暂停阻止新派发，不宣称自动终止已运行进程；界面区分暂停、执行中和停止。
- 讨论只一轮审查，最多三条建议；返工最多两轮。超时、登录失败、权限等待、报告不合法均停止并显示原因。
- “已知限制”不能豁免验收；BLOCKED 与 FAIL 分开；证据需关联验收项和版本。
- 模型输出是不可信输入，不能自行提升权限、修改执行策略或授权发布、删除等高风险动作。
- Token 只展示提供方真实返回值，注明缓存及累计口径，不保证节省比例。不做空闲轮询式模型调用。

## Antigravity 工作包：仅界面和独立验收

请先读取 DESIGN.md、本文件及 docs/contracts/ 下协议，再实施以下任务。

更新：后台已新增 docs/contracts/web-planning-v2.md 中的讨论、状态查询和批准接口。
请按真实接口接入按钮与状态，不再把这些项标为接口缺失。
需求修订也已加入同一协议：提供预填当前需求的“修改需求”表单，明确提交完整新需求，
不要把普通聊天文字当成替换需求。运行中不能修订。自由聊天仍不可用。

允许修改：web/、前端构建配置、由构建生成的 worktogether/static/、qa/antigravity/ 和 tests/acceptance/antigravity/。
不要修改：core.py、runtime.py、antigravity.py、discussion.py、server.py、数据库、CLI 或协议。缺失接口记录到 qa/antigravity/findings.md，不自行发明接口。

交付步骤：
1. 将生产静态资源改成从 React 源码构建；确认刷新页面加载同一份界面。不得继续维护两份交互逻辑。
2. 白底/浅灰、蓝色强调，左侧项目与任务，中间时间线和内容，右侧执行信息。移除装饰性 emoji 和重复入口；空状态说明真实能力。
3. 修正事件字段 kind/data；未知事件安全降级。轮询不得清空输入或抢走焦点。底部输入不能悄悄新建任务；后端不支持任务内消息时禁用并解释。
4. 把真实状态、错误、被测版本、报告证据清晰展示。未接通的自动讨论/开发按钮禁用，不能用假消息冒充真实 Agent 回复。
5. 验证空项目、长需求、长列表、失败/阻塞、窗口缩窄、轮询保留输入、刷新持久化与未知事件。附实际命令、结果、截图及未覆盖项。

提交简短交付说明：改了什么、如何验证、证据路径、仍需哪些后端接口。不要安装全局软件、发布服务或修改其他项目。
